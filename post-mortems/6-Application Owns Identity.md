# Application Owns Identity

*2026 September 19*

*Status: implemented.*

Building an undo layer on top of the canvas (Coollab's `177-Command and Edit.md`) turned up four places where the crate had quietly kept a decision that `1-Application Owns the Model.md` says is the application's. Each was a convenience - a minted id, a policy applied for you, a gesture collapsed to one event, a `&mut` handed to a node body - and each got in the way of the first application that wanted to decide for itself. This file records the sharper reading of "the application owns the model" that came out of it: **identity, policy and observability are part of the model too.**

## Alternatives considered

**A generic id type the application supplies, vs. the crate minting `NodeId(u64)`.** The crate minted ids monotonically and offered `add_node_with_id` to restore one. That is the crate deciding an identity scheme: a session counter, which cannot work across two peers or two documents merged, and which Coollab would have had to work around with `{ site, counter }` *inside the crate's type*. Now `Graph<N, I: NodeIdentifier>` takes the application's type (`Copy + Ord + Hash + Debug`), the application mints every id, and `add_node(id, ..)` is the only constructor - `mint_node_id` was never added and `add_node_with_id` disappeared, two functions for one operation collapsing into one. The cost is that `I` propagates through `Wire`, the pins, `CanvasEvent`, `Selection` and the layout maps. **No default type parameter**, though one was proposed: `Graph<MyNode>` silently inheriting an identity scheme is the crate deciding again, just quietly, and `Graph<MyNode, MyId>` makes every application decide once. `SequentialNodeId` is *offered* for applications that do not care - available, not implicit; the demo uses it. What the crate still asks of any scheme is that an id is never recycled.

**Policy above the primitives, vs. `connect(policy) -> Connected::New { displaced }`.** "Every mutation returns what its inverse needs" turned out to be two principles wearing one name. For `set_pos -> Option<Pos2>` and `remove_node -> RemovedNode` it is ordinary Rust (`HashMap::insert` returns the old value) and the removal's wire scan would only be duplicated outside: keep. For `connect(policy)` it was the crate deciding what a dropped wire means, performing collateral mutations and reporting them afterwards - and an undo layer wants the opposite, edits that each do one thing and invert 1:1. So `connect(wire)` just adds a wire, whatever is already on the input, and the `Single` displacement moved up into `Graph::apply` and `insert_into_wire`, the convenience layer for applications without undo, via a `displace(input, policy)` primitive. Refusing an occupied input in the crate was considered and rejected: a multi-wire input is a legitimate graph for some applications, and the crate does not model per-pin arity; an application with a one-wire rule checks it in its own edit layer.

**Reporting every frame of a drag, vs. one `NodesMoved` on release.** The crate collapsed a drag into one end-of-drag event and `1-Application Owns the Model.md` called that "one undo entry per drag by construction". It was the crate simplifying the application's life by withholding information: a plugin that reacts to a node moving, a peer mirroring the drag, or a user's recording of how they moved things were all impossible. Now `NodesMoved { moves, phase }` is reported every frame the pointer moves, naming *every* dragged node each time so the set is stable, then once more as `MovePhase::Finished` - the phase is what an application groups an undo entry on. The convenient behaviour is one `match` away for an application that wants it.

**`make_room` resolving synchronously, vs. sliding over frames and reporting at the end.** The slide-apart after a splice used to wait for the inserted node to be measured, animate the neighbours' positions in the view, and report the settled positions frames later as a separate `NodesMoved` - so a splice would have been *two* undo entries, the second un-sliding the neighbours without removing the node. Appending to an already-committed entry was rejected as fragile (the user can act during the slide). Instead `measure_node` lays the node out in an invisible sizing pass first - iterated until the size settles, since one pass is a few pixels off what a shown node ends at - and `make_room(graph, wire, inserted_rect, style)` returns the final positions **at once**, for the application to apply with the splice they belong to. Only the animation stays in the view: each slid node is drawn short of its new position by an offset that eases to zero. `MoveCause` was proposed to tag make-room moves and fold them into the previous entry; unnecessary once make-room emits no event at all.

**Node bodies see `&N`, not `&mut N`.** `1-Application Owns the Model.md` justified `Canvas::show(&mut Graph)` with "node bodies need `&mut` to their payload", while in the same breath insisting content is content-only and graph-changing intentions leave as events. The `&mut` was the loophole through which every future body widget would have bypassed an application's command layer. `NodeContent::body` and `header` take `&N`, `Canvas::show` takes `&Graph`, and the application's content type carries whatever sink it wants (Coollab's carries a command queue). A side benefit: transient widget state cannot be stashed in the payload any more.

**`SelectionChanged` as an event.** Selection stays view state (still not undoable, as `1-Application Owns the Model.md` decided), but the canvas now reports when it changed, so an application mirroring it - a properties panel, a script, a peer - is told rather than diffing each frame.
